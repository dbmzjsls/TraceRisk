# TraceRisk v3 阶段 6 评测、交付与求职包装设计

日期：2026-09-28。状态：设计、书面规格和实施计划已批准，进入实施。

## 目标与范围

阶段 6 在阶段 5 已完成的四领域规则、混合检索、AI 支持性校验、人工复核、不可变报告、工作流事件和七页界面之上，完成可重复的自动评测、四服务 Docker 运行环境、无真实模型依赖的 CI、端到端业务验收，以及可核验的演示和求职材料。

本阶段不新增风险规则、业务页面、数据库表、外部模型提供商或生产部署平台。所有指标、截图和求职描述必须由本阶段实际执行结果生成；历史阶段证据可以引用，但不能改写为新的执行结果。

## 固定约束

- 自动评测和端到端写入使用独立临时数据库，不能向保留数据库写入评测数据。
- CI 和默认 Docker 演示使用 Fake Embedding 与 Mock Model，不下载 BGE，不调用真实 LLM。
- Mock 和真实模式的结果分开记录。没有实际真实模型调用时，真实模式明确写为“未执行”，模型成本写为“不适用”，不得估算或填写零成本。
- 规则准确率、Recall@5、引用合法率、证据覆盖率和结构化输出成功率必须给出样本数、分子、分母和计算公式，不能只给百分比。
- Docker Compose 保留现有 `postgres_data` 命名卷和 PostgreSQL 服务；不重建、清空或替换保留卷。
- 端到端测试必须验证数据库结果和用户可见结果，不能只断言 HTTP 200 或页面元素存在。
- README、演示稿、面试说明和简历要点只使用实际通过的检查和评测数字；未通过或未执行的项目必须如实标注。

## 自动评测设计

`scripts/run_evaluation.py` 是阶段 6 的唯一汇总入口。它在明确指定的隔离数据库上运行评测测试和指标采集，生成机器可读结果及 `docs/evaluation/results.md`。脚本拒绝未显式标记为评测用途的数据库目标，并在运行前确认目标不等于当前保留应用数据库。它必须把本次 pytest 退出码、通过/失败/错误数和各指标组状态写入同一个版本化运行结果；任一必需测试或指标组失败时命令返回非零，并用本次失败结果替换“最新结果”，不能继续保留上一轮成功文件冒充本次运行。

评测分为四组：

1. **规则准确率**：使用固定的合成标注样例，逐领域比较规则命中、分值与预期结果。准确率按完全匹配样例数除以总样例数计算；报告同时列出 business、judicial、news、intellectual_property 的分项结果。
2. **检索 Recall@5**：复用阶段 4 的静态 `datasets/evaluation/retrieval_cases.jsonl`、同一检索流水线和既有计算函数。Fake 结果只证明管线可重复，不表述为语义模型质量。历史真实 BGE 结果可作为带来源日期的历史引用，阶段 6 不把它冒充本次运行。
3. **引用与证据**：引用合法率以持久化 AI 引用为样本，要求每条引用指向当前 Run 冻结检索集中的 Chunk，并通过 Evidence ID、内容哈希和连续摘录校验。证据覆盖率按需要证据支持的最终结论中至少有一条有效引用的结论数除以该类最终结论总数计算。分母为零时结果标记为 `not_applicable`，不能记为 100%。
4. **结构化输出**：使用 Mock Model 的固定场景，统计通过 Pydantic 结构校验、引用边界校验和支持性校验的模型响应。成功率按完整通过的响应数除以所有评测响应数计算；预期拒绝的非法结构另列为负向测试，不混入成功率分母。

评测结果按 `mock` 与 `real` 两个顶层部分记录。`mock` 包含本次运行标识、源数据快照、环境、样本数、指标和新鲜测试结果。`real` 只有在实际调用真实模型时才包含模型、调用次数、token 和成本；本阶段默认记录 `status: not_run` 和原因。JSON 与 Markdown 使用相同运行标识，Markdown 记录 JSON 内容哈希；写入采用临时文件和原子替换，并设置运行中标记。异常或中断必须清理临时文件、保留可诊断的本次状态并返回非零；数据库断连后仍在 `finally` 中清理本次拥有的隔离数据库。

`apps/api/tests/evaluation/test_rules.py`、`test_citations.py` 和 `test_workflow_recovery.py` 分别固定上述指标输入及恢复语义。工作流恢复测试覆盖 Outbox 重投、worker 失败后重试、新进程/重启恢复、重复复核和报告唯一性，并核对最终 Run 状态、Outbox 数量、ReviewDecision 数量、RiskReport 数量和报告快照字节稳定性。

## Docker 与服务拓扑

Compose 提供四个运行服务：

- `postgres`：继续使用固定 pgvector PostgreSQL 镜像、命名卷和 `pg_isready` 健康检查；
- `api`：执行 Alembic 升级后启动 Uvicorn，暴露 API 和 OpenAPI；
- `worker`：复用与 API 相同的后端镜像和环境，在一个受控启动器中同时运行现有 Outbox dispatcher 和 Procrastinate worker；任一职责异常退出时整个容器失败，关闭时同时取消两者；健康检查同时验证启动器存活、dispatcher 最近一次成功扫描以及 worker/队列循环存活；
- `web`：多阶段构建 Vue 应用，由轻量静态服务器提供页面，并把 `/api` 请求代理到 API，避免浏览器依赖宿主机地址。

`api` 和 `worker` 等待 PostgreSQL 健康；`web` 等待 API 健康。服务均提供容器健康检查，Compose 最终应显示四个服务健康。API 与 worker 使用 Mock/Fake 默认环境，且环境变量中不要求真实模型密钥。公开 API 创建调查后必须由部署中的 dispatcher 与 worker 自行推进，验收辅助程序不得手工调用 `dispatch_once` 代替服务职责。

`apps/api/Dockerfile` 使用锁文件安装生产依赖，不安装 `bge` 可选依赖。镜像以非 root 用户运行，并提供适用于 API 和 worker 的共同入口。`apps/web/Dockerfile` 固定 pnpm 锁文件安装与生产构建，最终镜像只包含构建产物和静态服务器配置。

Compose 启动不能自动清空、重建或重新填充已有数据库。数据库服务器初始化目标与应用目标使用不同变量：PostgreSQL 容器保持现有命名卷，而 API/worker 默认连接独立 Fake 演示库 `tracerisk_demo`，不能连接或重建保留的 BGE `tracerisk` 库。首次运行先只启动 PostgreSQL，再通过受保护的一次性命令创建或核验目标库，确认 `current_database()`，依次执行 Alembic、Procrastinate schema、LangGraph checkpoint schema、演示账号、合成目录和 Fake index 初始化，最后启动 API/worker/Web。已有保留卷和全新卷都使用同一顺序；日常启动不重复播种。临时验收库由同一生命周期助手创建并记录所有权，清理时断开连接并只删除本次创建且名称匹配的数据库。最终 Compose 验证显式携带已经初始化并核验的应用目标，且先只读确认保留库仍使用原 BGE index。

## CI 设计

GitHub Actions 在受支持的 Python 3.12 和项目固定 Node/pnpm 版本上运行。单个工作流可以拆分为 backend 与 frontend 两个并行 job：

- backend 启动隔离 PostgreSQL/pgvector service，安装默认依赖，执行 Alembic、pytest、Ruff、format check 和 strict mypy；
- frontend 固定 Node/pnpm，同时安装 Python 3.12、uv 与后端默认锁定依赖，因为 API 生成一致性会调用后端 OpenAPI 导出；随后执行 API 生成一致性、现有边界测试、lint、typecheck 和 build。

CI 显式设置 Mock Model、Fake Embedding 和禁用外部 tracing 的环境变量。工作流不得安装 `.[bge]`、不得缓存或下载句向量模型，也不得接收或调用真实 LLM 密钥。测试失败必须使 job 失败，不能使用 `continue-on-error` 掩盖结果。

## 端到端验收设计

`apps/web/e2e/investigation.spec.ts` 使用浏览器驱动真实 Web、API、worker 和隔离 PostgreSQL。测试数据来自幂等合成场景目录；每个场景拥有稳定标识，并且可以在空评测库中重复导入。测试通过 API 创建调查，通过部署中的真实 Outbox dispatcher 和 worker 处理业务，再从页面与数据库两侧核对结果。

八条验收路径为：

1. 低风险 Run 不进入复核，直接生成唯一报告；
2. 高风险 Run 进入复核，完成决定后恢复并生成报告；
3. 修改 AI 结论后，最终结论使用人工修改内容，报告仍保留原始 AI 输出；
4. 驳回 AI 结论后，该结论不进入最终结论，原始输出和决定仍可追溯；
5. 证据事实冲突即使规则分未达到阈值也强制复核；
6. 来源不足时规则分保持规则计算结果（可为零），并进入运行级复核；
7. Evidence ID、哈希、摘录或冻结集合不匹配的引用被拒绝，不产生持久化 AI Finding 或报告；
8. 相同幂等键重复提交复核、重复派发恢复任务和重放 worker 后，仍只有一个决定和一份报告。

浏览器测试避免依赖固定等待时间，以状态、SSE 事件和最终 API/数据库条件为等待边界。`docs/evaluation/e2e-checklist.md` 为每条路径记录前置场景、用户动作、用户可见断言、数据库断言和实际结果。

非法引用路径使用仅存在于 E2E 源目录的 worker 启动器和注入适配器：它替换同一 `worker` 服务的命令、挂载测试助手，仍运行真实 dispatcher、队列、工作流、引用校验和持久化，只对具名隔离场景的 Mock 返回值制造指定引用错误。该助手不复制进生产镜像，也不能由生产配置启用。测试必须证明该 worker 消费了目标 Run，并断言可见失败状态、持久失败事件及不存在 AIFinding/报告。

截图只在关键页面稳定后生成，且不得包含 Token、密码、Authorization 或数据库凭据。认证 E2E 禁用 Playwright 网络 trace 和 video；失败证据使用安全截图、经过字段白名单处理的状态/事件 JSON 和已脱敏日志。Compose 证据保存命令、退出码及脱敏后的结构摘要，不原样保存插值后的凭据。最终秘密扫描递归检查文本、压缩包和其他嵌套产物，并用已知合成秘密标记验证扫描器确实能检出。

## 错误处理与数据保护

- 评测脚本在数据库目标不明确、目标与保留数据库相同、迁移不完整或源数据快照不匹配时停止，不尝试自动修复保留数据。pytest 可继续使用现有、具备创建所有权和精确删除保护的 `tracerisk_test_<32 hex>` fixture；评测 CLI 和 E2E 分别只允许 `tracerisk_eval_<32 hex>` 与 `tracerisk_e2e_<32 hex>`。
- Docker 初始化脚本保持幂等；已经存在的账号、公司、证据和报告不被删除或覆盖。
- 工作流恢复测试对重试次数设置上限，并将预期失败与基础设施失败分开报告。
- 指标生成任何一组失败时，结果文档保留已完成的分项和失败原因，但阶段清单保持未完成。
- E2E 或截图失败时保留日志和可重复命令，不用拦截 fixture 冒充真实全栈验收。
- 所有提交给 CI、文档和评测产物的内容执行秘密扫描。

## 验证与完成标准

阶段 6 最终执行主计划列出的命令，并增加阶段 6 的聚焦评测、API 生成一致性、前端现有边界测试、E2E、Compose 健康检查、结果文档校验和秘密扫描。E2E 对应用数据库和 worker 命令的覆盖只在其受控生命周期内生效；无论成功或失败都先清理测试服务和自有数据库，随后用基础 Compose、正常 combined worker 和 `tracerisk_demo` 重建最终演示栈。最终四服务健康与工作流推进证据只在确认不存在测试助手挂载后采集，E2E 失败仍保持最终验收失败。

完成必须同时满足：

- 五项指标有可重复输入、公式、分子、分母和实际结果；Mock 与真实模式明确分开；
- Outbox、重试、重启、重复复核和报告唯一性均有自动测试；
- Compose 构建后四个服务健康，保留卷未被清空或替换；
- CI 覆盖主计划要求且不下载 BGE、不调用真实 LLM；
- 八条端到端路径均有页面和数据库证据；
- README、演示脚本、面试说明、架构文档、四张截图和简历要点完成，并只引用实际指标；
- 完整验证结果如实记录，所有发现的阶段 6 问题修复并复核；
- 只有证据齐备后才勾选阶段 6 的既有清单项，其他计划内容保持不变。

## 明确不做

- 不部署到云平台，不配置域名、TLS、镜像仓库或生产密钥管理。
- 不新增真实模型调用，不重新下载或重新评测 BGE。
- 不增加 Kubernetes、Redis、消息代理、监控平台或新的数据库迁移。
- 不新增产品页面、业务规则、模型能力或管理员功能。
- 不把 Mock 指标描述为真实模型质量，不把历史测试结果描述为本次执行结果。
