# TraceRisk 真实模型挑战评测设计

日期：2026-10-23

## 目标

为 TraceRisk 新增一套适合“大模型应用开发实习生”简历展示的真实模型评测。现有 35 条引用测试和 24 条规则测试继续作为 CI 回归门禁，不再把其通过率包装为模型质量成果。新评测使用约 40 条冻结挑战样本运行未经优化的真实基线，完成逐案例留痕、错误归因、单变量改进和同集复测，最终只依据实测结果生成报告、典型案例和简历表述。

评测不以 100% 通过为目标，不预设结果，不手填汇总数字。若真实模型端点、余额或运行环境阻止实验完成，报告必须保留失败事实，不得生成虚构对比。

## 选定方案

采用“隔离挑战评测 + 复用生产校验器”的混合方案。

挑战样本以冻结 Chunk 直接构造模型上下文，使用真实 DeepSeek OpenAI-compatible Chat Completions API 调用模型，并复用 TraceRisk 的生产 Pydantic Schema、`claim_code` 目录、引用完整性规则和证据支持性判断。该方案把评测焦点限定在模型生成、引用选择、证据支持判断和复核路由上，避免数据库、检索和工作流波动混入单变量实验。

不采用以下两个方案：

- 完整 PostgreSQL 工作流逐案例执行：产品真实性更高，但检索、数据库和工作流故障会与模型问题混杂，不利于单变量归因。
- 纯离线独立脚本：实现最轻，但不能证明结论符合 TraceRisk 的真实 Schema、引用校验和人工复核边界。

## 冻结边界

基线与复测共同冻结以下内容：

- 数据集文件及其 SHA-256。
- 模型名 `deepseek-flash`、API 基础地址 `https://api.deepseek.com`、非流式 Chat Completions 接口及模型参数。
- 除唯一改进变量外的 Prompt 内容。
- Python 3.12、项目 `uv.lock`、操作系统和关键依赖版本。
- 最大总尝试次数为 2；超时、限流和服务端错误可重试，永久错误不重试。
- 计价币种、输入/输出/缓存 Token 单价和价格依据日期。成本只由 API 返回的实际 usage 与冻结价格快照计算。
- 上下文 Chunk 顺序；除非实测选中的唯一改进变量就是上下文排序。

API Key 只从 `.env` 的 `MODEL_API_KEY` 读取，不进入运行清单、原始响应或报告。运行清单记录请求模型名、API 返回的模型标识（若存在）及运行时间；“真实模型版本”仅按服务端可观察信息表述，不猜测未返回的内部快照。

## 挑战数据集

文件为 `datasets/evaluation/model_challenge_cases.jsonl`，包含 40 条手工逐条策划的合成样本，每类 10 条：

1. 明确证据：唯一支持 Chunk 足以支持允许的 `claim_code`，期望接受。
2. 相似实体或相似数字误引：支持 Chunk 与实体名、案号、金额、日期或比例相近的迷惑 Chunk 同时出现，期望按金标拒绝或人工复核。
3. 不同来源冲突：同一企业、同一事实键、同一时间点的不同来源给出互斥值，保留双方且禁止模型擅自裁决，期望人工复核。
4. 证据不足：缺少必要事实、只有背景描述、来源不可用或事实字段不满足支持目录，期望拒绝或人工复核。

每条案例至少包含：

- `case_id`、类别、企业 ID、业务说明。
- 冻结 Chunk 列表及确定性 ID、哈希、来源、风险域、日期和结构化事实字段。
- 支持结论的 Chunk ID 列表。
- 迷惑性 Chunk ID 列表。
- 允许的 `claim_code` 列表。
- 期望处理方式：`accept`、`reject` 或 `manual_review`。
- 人工编写的判断理由。

数据加载时验证：总数和四类均衡、ID 唯一、哈希正确、支持/迷惑 Chunk 均存在、两者不重叠、`claim_code` 属于生产目录、期望处理方式有效、理由非空。模型输出与运行结果不得回写数据集。

“人工设计”在报告中准确表述为逐条手工策划的合成评测案例；不声称它来自真实用户、生产数据或统计抽样。

## 组件边界

新增 `apps/api/src/tracerisk/challenge_eval/`，按职责拆分：

- `schemas.py`：冻结案例、运行配置、逐尝试记录、逐案例结果和人工复核记录。
- `dataset.py`：JSONL 加载、契约校验和 SHA-256。
- `prompts.py`：基线 Prompt 与可选的唯一改进 Prompt；生产 Prompt 不在本任务中改动。
- `client.py`：真实 DeepSeek 调用、两次尝试边界、usage、延迟和原始响应脱敏。
- `validation.py`：将案例 Chunk 转换为生产 `RiskContext`，复用生产 Schema、claim 支持判断和引用边界。
- `scoring.py`：期望/实际处理、引用选择、字段差异和错误类型计算。
- `attribution.py`：结构、引用、证据支持性和人工判断归因，选择唯一改进问题。
- `reporting.py`：从逐案例 JSON 聚合汇总、Markdown 报告、典型案例和简历表述。
- `runner.py`：幂等执行、恢复、阶段冻结和单变量守卫。

新增 `scripts/run_model_challenge.py`，提供：

- `baseline`：运行未经优化的真实基线。
- `analyze`：只读取基线原始结果，完成归因并生成唯一改进配置。
- `improved`：在同一数据集和冻结环境运行复测。
- `compare`：生成前后对比及简历表述。
- `review`：对路由到人工复核的案例执行交互式计时复核。

## 执行与数据流

执行顺序固定为：

1. 校验数据集和环境，计算数据集、Prompt、依赖锁文件及运行配置哈希。
2. 逐案例构造相同格式的冻结上下文并运行基线。
3. 每次 HTTP 尝试结束后立即追加写入原始 JSONL；已完成案例按 `case_id` 和运行指纹跳过，实现安全恢复。
4. 解析模型 JSON，执行 Schema、引用完整性、`claim_code` 和证据支持性验证，得到实际处理方式。
5. 与金标对比并记录字段差异、错误类型、人工复核路由和诊断耗时。
6. 聚合基线归因，只选择出现最多且影响最大的一个问题。
7. 生成明确声明唯一允许变更项的改进配置。
8. 在同一冻结数据集上复测；运行器拒绝任何非允许字段变化。
9. 从两份原始 JSONL 生成汇总 JSON、对比 Markdown、典型案例和真实简历表述。

基线原始结果不可由复测覆盖。输出目录以运行 ID 区分，并保存机器可读清单。

## 逐案例记录

每条案例记录：

- 首次调用是否得到可解析且可校验的输出。
- 模型逻辑调用数、HTTP 尝试数和重试次数。
- 期望和实际的接受、拒绝或人工复核处理方式。
- 被路由到人工复核的原因。
- 人工修改字段数和实际人工复核耗时；未执行真实交互复核时为 `null`，并附 `not_measured` 原因。
- 引用错误类型与一级归因类别。
- 输入 Chunk 数、模型实际引用的唯一 Chunk 数和 ID。
- 输入、输出、缓存命中/未命中 Token；API 未返回的字段为 `null`。
- 依据冻结价格快照计算的案例成本；缺少必要 usage 时为 `null`，不估算。
- 每次模型调用耗时、案例总模型耗时和失败定位耗时。
- 脱敏原始响应、解析结果、验证反馈和字段差异。

失败定位耗时定义为模型尝试结束后，评测器完成解析、校验、归因和逐案例结果落盘所消耗的单调时钟时间。它是自动诊断耗时，不冒充人工排障工时。

人工复核数量是实际路由到复核的案例数。人工修改字段数在完成交互复核时记录实际修改；未进行人工复核时不使用金标差异冒充人工修改。

## 实际处理与评分规则

- 输出通过 Schema、所有引用边界和结构化支持性校验，且没有冲突或强制复核条件时为 `accept`。
- 输出为空，或明确拒绝生成不受支持结论，且符合案例的拒绝契约时为 `reject`。
- 存在来源冲突、开放自然语言扩展、覆盖不足，或模型明确建议复核且没有硬引用错误时为 `manual_review`。
- 硬引用错误、未知 `claim_code`、域不匹配或引用事实与声明矛盾不能通过“建议人工复核”变合法；其模型结论被拒绝，并保留错误归因。

报告不以单一“通过率”为主要成果。主要过程指标为：

- 首次可用案例数。
- 正确接受、正确拒绝和正确转人工复核数。
- 不必要人工复核和漏复核数。
- 错误引用案例数及类型分布。
- 人工修改字段总数和已测人工复核耗时。
- 模型逻辑调用、HTTP 尝试、重试、Token、成本、模型耗时和失败定位耗时。

可以提供处理一致性作为辅助计数，但简历表述优先使用与选中问题直接相关的过程指标变化。

## 归因和单变量改进

一级归因按以下顺序互斥分配：

1. `structure_error`：HTTP 成功但 JSON、Schema 或必需字段不可用。
2. `citation_error`：引用 ID、哈希、连续摘录、归属或冻结范围错误，包括选择迷惑 Chunk。
3. `support_error`：结构和引用合法，但 `claim_code`、事实方向、证据充分性或冲突处理错误。
4. `human_judgment`：没有前三类硬错误，但因开放文本、来源冲突或覆盖边界需要人工判断。

每个问题的优先分为“受影响案例数 × 固定影响权重”。影响权重在基线运行前写入冻结配置：导致错误接受或漏复核的权重最高，错误拒绝次之，不必要复核再次之，纯格式重试最低。若并列，依次比较错误案例数、已测人工修改字段数、失败定位耗时；仍并列时按上述归因顺序确定，确保选择可重复。

只修改与最高影响问题直接对应的一项：Prompt、校验反馈、上下文排序或人工复核路由。优先选择最小且可解释的改动，不保证一定修改 Prompt。改进运行清单显式保存 `changed_dimension`，运行器比较完整冻结配置并拒绝第二项变化。

模型供应商的非公开服务端变化无法由客户端完全控制。报告必须记录两次运行时间、返回模型标识和这一限制；若服务端标识不同，前后比较标记为受污染，不做强因果表述。

## 人工复核

`review` 命令逐条显示案例、Chunk、模型输出和验证反馈，以单调时钟从案例展示完成后开始计时，到复核者提交决定时结束。复核者可接受、拒绝或提交修改后的允许字段；工具记录修改字段名、数量和耗时，不保存复核者自由文本中的敏感信息。

没有真实人员完成交互步骤时，`review_duration_ms`、`human_modified_field_count` 和修改字段列表保持 `null`，汇总报告明确显示“未测量”。自动金标对比只作为评测差异，不能记为人工修改。

## 输出

输出位于 `docs/evaluation/model-challenge/`：

- 冻结运行配置与环境清单。
- 基线和改进运行的原始逐案例 JSONL。
- 基线和改进汇总 JSON。
- 前后对比 Markdown 报告。
- 典型成功、失败和人工复核案例。
- 可重复执行说明。
- 由最终汇总生成的单条简历表述。

简历表述必须包含“发现问题—完成改进—过程指标变化”，并同时注明真实模型、40 条小样本合成挑战集和非生产环境边界。若复测没有改善，简历表述如实说明实验结论，不改写为成功优化。

## 测试和验收

新增 `apps/api/tests/challenge_eval/`，覆盖：

- 数据集数量、四类均衡、ID、哈希、Chunk 引用和金标契约。
- DeepSeek 成功、重试、永久错误、usage 缺失和响应脱敏。
- Schema、引用、claim 支持、冲突和证据不足路由。
- 首次可用、引用错误、字段差异、Token、成本和耗时聚合。
- 一级归因互斥、影响评分、并列规则和单变量守卫。
- 中断恢复不重复调用已完成案例。
- 报告和简历数字全部来自原始 JSON，未测值不被填充。

现有 35 条引用测试和 24 条规则测试原样运行并只报告为 CI 回归门禁。相关新增测试、Ruff、格式检查和 mypy 必须通过。真实 API 测试不进入默认 CI，避免消耗密钥和引入供应商波动；CI 使用录制的最小响应夹具测试客户端和聚合逻辑，但不得把夹具结果写成真实模型成果。

验收完成条件：

1. 40 条冻结案例满足数据契约。
2. 真实基线完整运行，或诚实记录阻止运行的外部失败。
3. 原始逐案例数据可追溯到汇总数字。
4. 只选择并修改一个最高影响问题对应的变量。
5. 同一冻结数据集完成复测；若模型服务端标识变化则报告污染。
6. 生成对比报告、三类典型案例、复现命令、新增回归测试和基于实测结果的简历表述。

## 限制

- 数据是合成、小样本、手工策划的挑战集，不代表真实企业风险分布。
- 样本标签是评测设计判断，未经过多名领域专家一致性检验。
- DeepSeek 是运行时外部服务；模型内部版本、负载和服务端实现不完全可控。
- 本地非生产环境的延迟、重试和成本不能外推到生产吞吐。
- 评测隔离了数据库和检索，不衡量真实召回质量或端到端用户体验。
- 未完成真实交互复核时，不报告人工复核耗时或人工修改字段数。
- 单次前后实验只能支持对该冻结样本和运行条件的有限结论，不能证明普遍提升。
