# TraceRisk v3 Stage 6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce reproducible evaluation evidence, a healthy four-service Docker stack, offline-safe CI, eight full-stack acceptance paths, and evidence-backed delivery and interview materials.

**Architecture:** Existing PostgreSQL, FastAPI, Procrastinate worker, Vue application, rules, retrieval, Mock Model, review flow, immutable reports, and SSE remain the product architecture. Stage 6 adds isolated evaluation orchestration, container and CI entry points, real-stack Playwright acceptance, and documentation; evaluation and E2E writes stay in explicitly named disposable databases while the retained database is read-only for compatibility checks.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 17/pgvector, Procrastinate, LangGraph, pytest, Ruff, strict mypy, Vue 3, TypeScript, Vite, pnpm, Playwright, Docker Compose, GitHub Actions, Markdown, Mermaid.

## Global constraints

- Implement the approved specification at `docs/superpowers/specs/2026-09-28-stage-6-design.md` and the four Stage 6 tasks in `TraceRisk-v3-实施计划.md`.
- Do not add business features, rules, pages, database tables, migrations, external model providers, production deployment, Redis, Kubernetes, monitoring services, or cloud infrastructure.
- Evaluation CLI and E2E writes use generated database names matching `tracerisk_eval_<32 lowercase hex>` or `tracerisk_e2e_<32 lowercase hex>`. Existing pytest remains allowed to use its owned `tracerisk_test_<32 lowercase hex>` fixture. Destructive database cleanup must verify the applicable exact pattern and may drop only the database created by that run.
- Preserve the existing `tracerisk` database and `postgres_data` named volume. Capture its revision, row counts, primary-key sets, and canonical row hashes before Stage 6 runtime work; after every acceptance group, prove original rows remain unchanged. Never run `docker compose down -v`, delete the named volume, reset the retained database, or seed over existing rows.
- Separate the PostgreSQL server initialization database from the application target. Docker API/worker default to an explicitly provisioned Fake `tracerisk_demo` database; they must never point Fake settings at or rebuild the retained BGE `tracerisk` database. Fresh volumes, existing retained volumes, disposable runs, and final validation all use the guarded lifecycle sequence in this plan.
- Default Docker, CI, evaluation, demo, and E2E use `MODEL_ADAPTER=mock`, `EMBEDDING_PROVIDER=fake`, `EMBEDDING_MODEL=fake-sha256-v1`, and disabled LangSmith tracing. Do not install the `bge` extra, download BGE, or call a real LLM.
- Keep Mock and real results separate. Real-model status is `not_run` unless a real call actually occurs; do not estimate tokens or cost and do not report zero as an observed cost.
- Each metric records numerator, denominator, formula, sample identifiers, source snapshot hash, mode, and limitations. A zero denominator is `not_applicable`, never 100%.
- Browser acceptance uses the real Web/API/worker/PostgreSQL stack and database assertions. Intercepted fixtures may test UI error rendering but cannot satisfy any of the eight Stage 6 E2E checklist paths.
- Screenshots and artifacts contain no password, JWT, Authorization header, idempotency key, model key, database password, or connection string. Run a final secret scan.
- The directory is not a Git repository. Numbered source packages, task reports, independent reviews, hashes, and `.superpowers/sdd/stage-6-progress.md` replace commits and diffs.
